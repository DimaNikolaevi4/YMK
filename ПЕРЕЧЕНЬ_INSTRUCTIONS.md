# ПЕРЕЧЕНЬ МАТЕРИАЛОВ — методика формирования

> Этот документ — согласованный регламент того, **как** мы автоматизируем
> создание «Перечня материалов для подготовки студентов к промежуточной аттестации».
> Используется как стартовая точка для ИИ-агента и как регламент для преподавателя.
>
> **Утверждённые решения (от 2026-10-22):**
> 1. ✅ Списки студентов всегда генерируются **пустыми** (только заголовок группы +
>    подпись преподавателя). ФИО и даты преподаватель вписывает вручную в готовом .docx.
> 2. ✅ Эталон оформления — будет создан **новый «сводный эталон»** (отдельная задача
>    после наведения порядка в репо, см. раздел 10).
> 3. ✅ Образцы сконвертированы из `.doc` в `.docx` — доступны для парсинга через
>    `python-docx`.
>
> Файл будет дорабатываться по мере реализации.

## 1. Анатомия документа

Все 4 образца в папке `Перечни/` построены по одному и тому же каркасу. Различаются
только наполнением конкретных блоков (есть/нет курсовой, 1/2 группы, число практик).

3. Форма контроля (диф. зачёт vs экзамен/курсовой).
4. Перечень тем/работ/вопросов — берётся из РП.

## 3. Варианты подхода (обсуждение)

### Вариант A — Полностью ручной (Word-шаблон)
Преподаватель открывает эталонный `.doc`, копирует, заменяет текст. Плюсы — ничего программировать не надо. Минусы — каждый раз ручная работа, легко ошибиться в нумерации и заголовках, нет валидации.

### Вариант B — Генератор по JSON (как для КТП) **[рекомендуется]**
Скрипт `scripts/generate_perechen_docx.py` читает JSON-данные и собирает `.docx` по эталону через `python-docx`. Структура JSON — простой, человекочитаемый. Плюсы — повторяемость, валидация, переиспользование шаблонов и наработок из КТП. Минусы — нужно написать скрипт (~400–600 строк).

### Вариант C — Конвертация из РП автоматически
Скрипт парсит РП `.doc`/.docx` напрямую в ПЕРЕЧЕНЬ без промежуточного JSON. Плюсы — минимум ручных шагов. Минусы — РП имеют разную структуру по годам, парсинг хрупкий; правки после генерации делать неудобно.

**Итог обсуждения:** выбираем **Вариант B** — он совпадает по подходу с уже работающим генератором КТП, что:
- повторно использует наработки (`generate_ktp_docx.py`, `validate_ktp.py`);
- даёт преподавателю контроль над данными через редактируемый JSON;
- позволяет проводить валидацию до того, как документ уйдёт в печать.

## 6. Алгоритм сборки документа (12 шагов)

```
Шаг 1.  Прочитать JSON-данные (схема раздела 4).
Шаг 2.  Открыть эталонный .docx как шаблон (или собирать с нуля через python-docx).
Шаг 3.  Заполнить ТИТУЛЬНЫЙ БЛОК: подставить meta.*, approval.*.
        — Даты/протоколы остаются пустыми (подписываются вручную).
Шаг 4.  Заполнить таблицу КОНТРОЛЬ ЗНАНИЙ по control[].
Шаг 5.  Заполнить блок ТРЕБОВАНИЯ К РЕЗУЛЬТАТАМ:
        — 5 подсекций с подзаголовками; пустые подсекции (вариативная часть) не выводить.
Шаг 6.  Заполнить таблицу ПЕРЕЧЕНЬ РАБОТ:
        — Колонки: «Наименование тем» | «Прак./Лаб. работа» | «Сам. работа».
        — Объединить ячейки раздела (merge по вертикали в python-docx).
        — Каждая тема = одна логическая строка; работы внутри — список через перенос строки.
Шаг 7.  Если course_project != null → вставить блок «Курсовое проектирование»
        (задание, структура пояснительной записки, графическая часть, информационная часть).
Шаг 8.  Вставить экзаменационные вопросы из exam_questions[] (нумерованный список).
Шаг 9.  Вставить критерии оценки (5/4/3/2) — шаблон выбирается по criteria: short/extended.
Шаг 10. Для каждой группы из student_lists[]:
        — Заголовок «Студенты группы [ГРУППА] ознакомлены с материалами промежуточной аттестации:»
        — Таблица: № | ФИО | Дата | Подпись
        — ⚠️ ПО УТВЕРЖДЁННОМУ РЕШЕНИЮ: таблица всегда выводится ПУСТОЙ
          (student_list_empty_rows пустых строк с пустыми ячейками №/ФИО/Дата/Подпись).
          ФИО вписываются вручную после генерации в готовом .docx.
        — Подпись преподавателя в конце.
Шаг 11. Сохранить .docx в Перечни/ с именем «перечень [МДК].docx».
Шаг 12. Запустить валидатор (см. раздел 7).
```

## 7. Валидация (какие проверки включить)

| # | Проверка | Критерий |
|---|---|---|
| 1 | Заполнены ли обязательные поля meta | study_year, mdk_code, mdk_title, groups, teachers |
| 2 | Есть ли хотя бы одна форма контроля | `len(control) >= 1` |
| 3 | Есть ли хоть одна тема в works_table | `len(works_table[...].sections[...].topics) >= 1` |
| 4 | Склеены ли №№ практических работ по разделу | проверка монотонности |
| 5 | Совпадает ли список групп в meta и student_lists | множества равны |
| 6 | Совпадает ли число преподавателей и подписей | `len(teachers) == len(student_lists[].teacher_sign)` (если 1:1) |
| 7 | Если есть курсовой проект — заполнены ли все 4 части | explanatory, graphical, information, assignment |
| 8 | Есть ли вопросы к зачёту, если форма контроля = диф. зачёт | `len(exam_questions) > 0` |
| 9 | ~~Численность студентов > 0 по каждой группе~~ | ⚠️ отменено по решению: список всегда пустой, генератор рисует `student_list_empty_rows` пустых строк для ручного ввода. Проверка: таблица для каждой группы существует и содержит ровно `student_list_empty_rows` строк |
| 10 | Шрифты/размеры соответствуют эталону | Times New Roman, титул 12pt, таблицы 10pt |
| 11 | Нет пустых строк в начале/конце таблиц | структурная проверка |
| 12 | Имя выходного файла соответствует шаблону | «перечень [МДК].docx» |
